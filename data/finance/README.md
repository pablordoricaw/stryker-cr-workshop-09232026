# Finance reference data

This entirely synthetic dataset gives the Orthopedics workshop 25 finance PDFs
and 3,000 sales transactions. No real Stryker, customer, employee, or patient
data is present. Fixed seed `20260923` makes every generated byte reproducible.

## Contents

- `documents/` has five two-page PDFs in each ground-truth class directory and
  `document_manifest.csv` records the expected class and subtype. Layouts and
  labels vary; the `other` examples deliberately mention invoices, orders,
  pricing, and quarters so classification cannot rely on one keyword.
- `transactional/delta/sales_transactions/` is a readable Delta v0 fallback
  table with Change Data Feed enabled in its table properties.
- `transactional/lakebase/` has the same 3,000 rows as CSV, PostgreSQL DDL in
  `schema.sql`, and an idempotent psql loader in `load.sql`.
- `transactional/checksums.sha256` covers every generated artifact.

The sales data spans October 2025 through June 2026. Customer and product mix
are intentionally skewed, and Northeast sales receive deeper concessions
during an April–May procedure-kit supply recovery. This gives later exercises
a traceable regional margin story rather than flat random data.

## Re-run and validate

Run from the repository root. `uv` reads the maintainer-only script metadata and
creates an isolated environment; no Databricks workspace or database is used.

```bash
uv run --script generators/finance/generate.py
uv run --script generators/finance/generate.py --validate-only
uv run --script generators/finance/generate.py --check-reproducible
```

The last command generates into two temporary directories, reads every PDF and
Delta table, parses the PostgreSQL DDL, checks transaction arithmetic, and
requires byte-identical SHA-256 hashes.

## Loading either transactional path

Delta fallback (after copying the committed directory to a workspace-accessible
location):

```python
sales = spark.read.format("delta").load("<path>/sales_transactions")
```

Lakebase/PostgreSQL, from the repository root using a regular PostgreSQL URL:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 \
  -f data/finance/transactional/lakebase/schema.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 \
  -f data/finance/transactional/lakebase/load.sql
```

For Lakebase OAuth connectivity, the same files can be passed through the
Databricks psql wrapper (choose the project and CLI profile explicitly):

```bash
databricks psql --project <PROJECT_ID> --profile <PROFILE> -- \
  -f data/finance/transactional/lakebase/schema.sql
databricks psql --project <PROJECT_ID> --profile <PROFILE> -- \
  -f data/finance/transactional/lakebase/load.sql
```

`load.sql` truncates and reloads `finance_seed.sales_transactions`, so it is
safe to repeat for workshop setup. Configure the later Lakebase CDF ingestion
before loading when the initial insert events themselves must be captured.

## Extraction-field contract for issue #6

After `ai_parse_document` and `ai_classify`, issue #6 should route each class to
an `ai_extract` schema with these target fields:

| Expected class | Target fields |
| --- | --- |
| `vendor_invoice` | `invoice_number`, `vendor_name`, `invoice_date`, `due_date`, `purchase_order_number`, `currency`, `subtotal`, `tax_amount`, `freight_amount`, `total_amount`, `line_items` (`item`, `description`, `quantity`, `unit_price`, `line_amount`) |
| `purchase_order` | `purchase_order_number`, `buyer_name`, `vendor_name`, `order_date`, `requested_delivery_date`, `ship_to`, `payment_terms`, `currency`, `total_amount`, `line_items` (`line_number`, `description`, `quantity`, `unit_price`, `line_amount`) |
| `sales_contract_pricing_agreement` | `agreement_id`, `customer_name`, `effective_date`, `expiration_date`, `currency`, `minimum_procedure_commitment`, `rebate_terms`, `governing_law`, `covered_products` (`sku`, `product_family`, `list_price`, `discount_pct`, `contract_price`) |
| `quarterly_financial_statement` | `entity_name`, `reporting_period`, `period_end_date`, `currency_scale`, `net_sales`, `cost_of_sales`, `gross_profit`, `operating_income`, `net_income`, `cash_and_equivalents` |
| `other` | `document_subtype`, `document_number`, `document_date`, `issuer_or_preparer`, `counterparty_or_cost_center`, `amount`, `currency`, `referenced_documents` |

Dates use ISO `YYYY-MM-DD`, monetary values are numeric USD amounts, and rates
are decimals (for example, `0.1800` for 18%). Missing fields should remain null,
not be inferred from a different document class.
